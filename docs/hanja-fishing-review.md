# 한자 낚시터 一~十 MVP 독립 검토

검토일: 2026-10-26. 대상: 한자를 처음 배우는 초등학교 2학년 두 아이를 가정한 숫자 10자 시안.

## 검토 범위와 증거 수준

- **확인된 사실**: `docs/hanja-fishing-design.md` v0.1 전체를 읽었습니다. 아래 줄 번호는 이때 읽은 문서 기준입니다. 최초 확인 때 `hanja/`에는 파일이 없었습니다.
- **검토 방법**: 설계와 구현 소스의 정적 검토 및 기존 엔진 단위 테스트 실행입니다. 실제 아이 관찰, 사용자 시험, 브라우저 실행, 태블릿 터치, 음성 청취, 화면 대비 측정은 하지 않았습니다. 아래 사용자 시험 항목은 향후 수행할 제안입니다.
- **판단/제안**: 초2에게 맞을 가능성과 개선 방향에 대한 검토자 판단입니다. 아이들의 실제 한글 읽기 능력, 선행 한자 지식, 조작 능력은 확인하지 않았습니다. 특정 문항 수·시간·정답률은 검증된 연령 규준이 아닙니다.
- **외부 자료 확인**: W3C 접근성 해설과 IES 학습 지침의 관련 내용을 확인했습니다. 이 게임의 WCAG 준수나 학습 효과가 입증되었다는 뜻은 아닙니다.
- **공식 기준 미검증**: 한국어문회 배정표, 표준 훈음, 급수별 출제·쓰기 범위, 합격선, 한국식 필순·자형, 음성·글꼴·데이터 라이선스는 이번 검토에서 공식 원문과 대조하지 않았습니다. 설계의 해당 주장을 확인 사실로 취급하지 않습니다.

## 결론

**성인과 함께 하는 짧은 학습·조작 탐색용 MVP로는 조건부 적용 가능합니다.** 먼저 소개하고, 두 방향으로 골라 보고, 오답에도 포획을 보장하고, 경쟁을 배제하는 방향은 유지할 만합니다. 다만 이 시안만으로 ‘10자 숙달’이나 ‘시험 준비 완료’를 판정해서는 안 됩니다.

초기 설계 검토에서 **숙련도를 실제보다 높게 기록하는 경로와 접근 불가능한 필수 조작**을 최우선 위험으로 보았습니다. 이후 도움받음 기록 분리와 릴 건너뛰기, 일반 안내 TTS, 다음 문제 초점 지정 등 보완을 소스에서 확인했습니다. 마지막으로 남았던 완주 후 재시작 소개의 쉬기 누락도 `start()`의 상태 초기화로 코드상 수정된 것을 확인했습니다. 이번 검토에서 제기한 P1 사항은 소스 수정 확인 상태이며, 모든 사용을 막는 P0 치명 결함은 확인하지 못했습니다. 현재 판단은 마지막 ‘최종 코드 재확인 및 결론’이 우선합니다. 실행·사용자 검증으로 무결함을 확인한 뜻은 아닙니다.

## 초기 설계 검토: 위험과 적용 조건

아래 P0/P1 표기는 초기 설계의 위험 우선순위입니다. 이후 구현 검토의 지적은 당시 스냅샷을 기록한 것이며, 현재 반영 상태는 마지막 ‘최종 코드 재확인 및 결론’이 우선합니다.

### P0-1. 힌트 후 정답과 독립 정답을 구분해야 합니다

**근거**: 설계 43줄은 오답 뒤 정답을 빛나게 하여 재선택시키고, 99줄은 맞히면 숙련도가 오른다고만 정합니다. 한 문항에서 오답과 재시도의 처리 단위, 힌트 사용 여부, 중복 보상 규칙은 없습니다.

**위험 시나리오**: 몰라서 틀린 뒤 빛나는 물고기를 누른 답도 독립 정답처럼 저장하면 복습 간격이 늘어납니다. 반대로 오답마다 강등하면 조작 실수나 연타로 과도하게 내려갈 수 있습니다. 이는 현재 구현에서 재현된 버그가 아니라 설계상 열린 경로입니다.

**제안**:

- 한 문항에 첫 응답, 힌트 여부, 최종 완료를 따로 기록합니다. 훈음→한자와 한자→훈음 기록도 구분합니다.
- 포획·격려는 힌트 뒤에도 제공합니다. 숙련도 상승은 힌트 없는 첫 응답에만 허용하며, 동일 문항에서 중복 상승하지 않게 합니다.
- 오답은 “다시 볼 글자”로 예약합니다. 같은 글자를 바로 강조해 누르게 한 결과는 복습 성공으로 계산하지 않습니다.
- 2~3개 다른 문제를 거친 뒤 위치를 바꿔 다시 묻고 다음 날에도 확인합니다. 이 간격은 MVP 운영 제안이며 검증된 최적값은 아닙니다.

**수용 조건**: ‘오답→정답 공개→재선택’은 포획 완료 1회, 독립 정답 0회로 기록되고, 릴 성공 여부가 학습 기록을 바꾸지 않아야 합니다.

### P0-2. 접근 가능한 정지 보기와 릴 대체 동작이 필요합니다

**근거**: 설계 41~42줄은 움직이는 물고기와 누르기·놓기 타이밍을 사용합니다. 138줄은 canvas 구현을 정하지만 키보드, 보조기술, 움직임 감소, 음성 불가 시 경로는 명시하지 않습니다. 탭도 허용한다는 점은 긍정적입니다.

**위험 시나리오**: 한자를 알아도 움직이는 작은 물고기를 누르지 못하거나 릴을 놓는 시점을 놓칠 수 있습니다. canvas 그림만 제공하면 보조기술이 문제·보기를 식별하지 못할 수 있습니다. 무음 환경에서 음성만 문제를 제공하면 풀 수 없습니다.

**제안**:

- 문제를 푸는 동안 물고기의 위치와 글자는 고정하거나, 동일한 선택을 할 수 있는 정지된 HTML 버튼을 제공합니다. 글자는 좌우 반전·기울기·물결 왜곡 없이 둡니다.
- ‘바로 잡기/자동 릴’ 버튼으로 타이밍 없이 같은 기본 보상과 진행을 제공합니다. 누른 채 이탈하거나 화면을 전환해도 갇히지 않게 합니다.
- 문제 훈음은 글로도 표시하고 ‘다시 듣기’를 제공합니다. 음성 오류·미지원 상태에서도 진행 가능해야 합니다.
- 키보드 초점·선택·결과 알림을 제공합니다. 한자 고르기 문제의 보기 접근성 이름에 정답 훈음을 붙여 답이 노출되지 않도록 합니다. 화면낭독기를 위한 대체 활동은 시각적 자형 인식과 별도 능력으로 기록해야 합니다.
- ‘움직임 줄이기’로 수영·물결·포획 애니메이션을 줄입니다. 정답 표시는 색 외에 테두리·기호·글을 병행합니다.

**수용 조건**: 소리를 끄고, 드래그와 길게 누르기를 쓰지 않고, 움직임을 멈춘 상태에서도 소개→문제→오답 복구→포획→종료가 가능해야 합니다. 이 조건은 아직 실행 확인하지 않았습니다.

### P1-1. 새 글자 10개와 5분·월척 5문항의 관계를 정해야 합니다

**근거**: 설계 27줄은 한 포인트 10자, 32~40줄은 약 5분에 새 글자 3~4자 소개, 44줄은 월척 5문항입니다. 나머지 글자를 언제 소개할지 불명확합니다. MVP에서 복습 어항은 후속 단계입니다(153줄).

**제안**: 첫 놀이를 一二三, 다음을 四五六, 다음을 七八九十 등 작은 묶음으로 나누고, 보기에도 소개한 글자만 넣습니다. 아직 2자만 소개했다면 3보기를 맞추려고 미소개 글자를 넣지 말고 소개를 먼저 마칩니다. 3~4자 묶음은 출발 가설이며 아이 반응에 따라 줄이십시오. 획이 단순하다는 이유로 四~十까지 모두 쉽다고 가정하지 않습니다.

월척 5문항은 ‘오늘 놀이 완료’로 표시합니다. 5문항으로는 10자를 한 번씩도 확인할 수 없고, 양방향 확인은 최소 20개의 서로 다른 글자·방향 조합입니다. 이를 한 회차에 몰아넣지 말고 여러 짧은 회차와 다음 날 확인에 나눕니다. 3지선다 독립 추측으로 5문항을 모두 맞힐 확률은 (1/3)^5≈0.41%이나, 힌트 뒤 재시도가 허용되면 이 수치를 숙달 근거로 쓸 수 없습니다. 한 번의 선택 성공도 자유 회상을 입증하지 않습니다.

**수용 조건**: 미소개 글자가 정답·오답 보기로 나오지 않고, 월척 완료와 글자별 학습 기록이 별도로 표시되어야 합니다. MVP에 완전한 복습 어항이 없어도 ‘다시 볼 글자’와 다음 접속 때 재확인은 필요합니다.

### P1-2. 숫자 뜻·한국어 수 이름·훈음을 연결해야 합니다

**근거**: 설계는 소개 카드에 그림과 훈음을 넣지만 숫자 10자의 실제 카드 내용은 없습니다. 양방향 선택은 글자와 훈음의 대응을 연습할 뿐, 수량 이해나 스스로 읽기까지 확인하지 않습니다.

**제안**: 예를 들어 ‘三 / 셋 삼 / 3 / 점 세 개’를 소개 카드에 연결합니다. “셋은 뜻, 삼은 한자 소리”를 짧게 알려 주십시오. 四부터는 획 수를 숫자 값처럼 가르치지 않습니다. 十에 획 두 개가 있다고 ‘둘’로 연결하는 식의 혼동을 피합니다. 그림은 기억 보조로 쓰되 실제 글자 유래라고 단정하지 않습니다.

한자→훈음 문제에서는 문제 한자의 훈음을 자동으로 읽어 답을 알려 주지 않도록 합니다. 소개·정답 피드백의 음성과 문제 제시의 음성을 구분하십시오. 쉬운 수량 문제만으로 한자 독음을 안다고 기록하지도 않습니다. 예: ‘三은 셋 삼’은 검토 예시이며 시험용 표준 훈음은 공식 대조가 필요합니다.

### P1-3. 오답 안내는 목표 글자와 비교 가능해야 합니다

**근거**: 설계 43줄은 선택한 글자의 훈음을 들려주고 정답을 빛나게 합니다. 정답을 얼마나 보여 주는지, 다시 듣기·계속 버튼, 연속 오답 시 탈출은 명시하지 않았습니다.

**제안**: “이건 둘 이예요. 찾는 건 셋 삼이에요.”처럼 선택 글자와 목표 글자를 큰 글자·훈음으로 함께 보여 주고, 아이가 ‘다시 해보기’를 누를 때까지 읽을 시간을 줍니다. 잘못 누른 횟수를 아이 앞에서 누적 표시하거나 월척을 처음부터 다시 시작하지 않습니다. 같은 문항에서 두 번 어려워하면 함께 답을 보고 포획하게 하되 ‘도움받음’으로 남깁니다. 비슷한 글자 비교는 해당 글자를 모두 소개한 뒤 시작합니다. 숫자만 다루는 MVP에 人·入·目·士 같은 범위 밖 오답을 넣지 않습니다.

### P1-4. 운동 보너스와 학습 숙련도를 시각적으로 분리해야 합니다

**근거**: 릴 성공은 큰 물고기 보너스(42줄), 높은 숙련도도 큰·황금 물고기(98~102줄)입니다. 같은 크기 표현이 다른 의미를 가집니다. 오답 때 숙련도가 내려가므로 어항이 줄어드는 벌처럼 느껴질 가능성도 있습니다.

**제안**: 릴 결과는 물방울 장식 같은 일회 효과로, 학습 상태는 ‘처음 만남 / 다시 보기 / 혼자 맞힘’ 같은 글자·기호로 구분합니다. 수집한 물고기·꾸미기는 오답으로 회수하지 않습니다. 느린 조작이나 자동 릴에도 같은 기본 포획·도감 진입을 주고 보너스 때문에 진도·복습이 잠기지 않게 합니다. 확률 보상·일일 연속 접속 강요는 MVP에 추가하지 마십시오.

### P1-5. 종료·저장·아이별 기록은 짧은 놀이의 일부입니다

**근거**: MVP에 기기 저장은 있지만 저장 실패, 형제 프로필, 중단 지점, 하루 제한의 MVP 포함 여부는 없습니다. 부모 화면과 시간 제한은 장기 설계에만 있습니다.

**제안**: 문항 경계에서 나가기·쉬기를 제공하고 저장 성공 여부를 사실대로 표시합니다. 이어하기에서 포획 보상을 중복 지급하거나 응답을 중복 기록하지 않도록 합니다. 두 기기 각각 한 아이를 쓰는지, 한 기기를 공유하는지 명시하고 공유 시 기록을 분리합니다. 초기화는 아이가 쉽게 누르지 않도록 합니다. 기기 저장은 기기 간 동기화·영구 백업이라고 안내하지 않습니다. ‘오늘은 여기까지’ 종료는 꾸미기·추가 릴로 계속 붙잡지 않도록 합니다.

## 접근성 기준과 아동용 권고의 구분

- **확인한 공식 접근성 기준의 해설**: W3C [2.5.8 Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)는 AA 최소 24×24 CSS px 또는 규정된 간격·예외를 설명합니다. 이것이 초2에게 충분한 터치 크기라는 뜻은 아닙니다. **본 검토 제안**은 주요 버튼과 보기 터치 영역을 우선 48×48 CSS px 이상으로 시작하고 겹치지 않게 배치하는 것입니다. 실제 적정 크기는 태블릿 시험이 필요합니다.
- [2.5.7 Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)는 본질적 예외 등을 제외하고 드래그 없는 단일 포인터 대안을 요구합니다. 길게 누르기·놓기 릴에 자동 릴을 제공하라는 권고는 더 넓은 조작 접근성 판단이며 이 조항만의 직접 요구라고 주장하지 않습니다.
- [1.4.1 Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)는 의미를 색만으로 전달하지 않도록 합니다. 초록 게이지·정답 반짝임에 글과 형태 표시를 병행하십시오.
- [1.4.3 Contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)는 일반 텍스트 4.5:1, 정의에 맞는 큰 글자 3:1의 최소 대비를 설명합니다. 수채 배경 위 한자도 읽어야 할 정보입니다. 최종 배경·물고기색·한자색 조합별로 측정해야 하며, ‘먹색’이라는 서술만으로 통과 판정할 수 없습니다.

한글 안내와 한자를 200% 확대했을 때 잘림, 세로·가로 방향, 초점 표시, 화면낭독기 흐름, 음성 재생 실패·중첩은 아직 확인하지 않았습니다. 위 네 항목만으로 전체 WCAG 준수를 판정하지 않습니다.

## 학습 근거의 적용 한계

IES의 [Organizing Instruction and Study to Improve Student Learning](https://ies.ed.gov/ncee/wwc/PracticeGuide/1)는 시간 간격을 둔 학습, 그림과 설명의 결합, 퀴즈를 통한 재노출·회상을 권고합니다. 따라서 소개→선택→시간을 둔 재확인을 제안할 근거는 있습니다. 그러나 이 자료는 한국 초2 대상 한자 낚시 게임의 효과, 5분 회차, 3보기, 1·3·7일 간격, 새 글자 3~4개가 최적임을 입증하지 않습니다. 이 설계에 적용하는 것은 검토자의 추론입니다.

## MVP 적용 가능 조건과 후속 관찰안

다음 조건이 충족되면 보호자가 곁에 있는 탐색용 시안으로 적용할 수 있다고 판단합니다. 제품 출시나 학습 효과 인증 조건을 뜻하지 않습니다.

1. 숫자 10자와 양방향 보기의 대응이 일관되고, 소개 전 문항·범위 밖 오답·정답 중복이 없습니다. 시험용 훈음·자형은 별도 대조 전 ‘검증 완료’로 표시하지 않습니다.
2. 첫 응답·도움받음·놀이 완료를 구분하고, 릴 결과는 숙련도에 영향을 주지 않습니다.
3. 무음·정지 보기·자동 릴로 전 과정을 진행할 수 있고, 오답을 반복해도 탈출·완료가 가능합니다.
4. 월척은 완료 기념이며 10자 숙달·시험 합격을 선언하지 않습니다. 다음 날 재확인할 글자를 남깁니다.
5. 원하는 문항 경계에서 끝낼 수 있고 저장·이어하기·아이별 기록의 범위가 명확합니다.

**향후 실제 관찰 제안(미수행)**: 두 아이를 각각 짧게 관찰하며 보호자가 설명한 횟수, 글자를 알지만 터치에 실패한 횟수, 도움 전 첫 응답, 릴 건너뛰기 선호, 스스로 그만둘 수 있는지를 기록하십시오. 다음 날 물고기 색·위치 단서 없이 숫자 글자를 다시 보여 주어 훈음을 묻고, 가능한 경우 다른 인쇄 글꼴에서도 확인하십시오. 두 아이의 결과로 연령 전체의 효과를 일반화하지 마십시오. 조작 실수가 반복되면 글자 난이도를 낮추기 전에 정지 보기·터치 영역부터 조정합니다.

### 실제 구현에서 우선 수정할 문제

#### 구현 P1-A. 이름표 문제에서 TTS가 답의 독음을 읽을 수 있습니다

**소스 사실**: `game.js:22`의 `readQuestion()`은 `type==='name'`일 때 `${t.ch}의 뜻과 소리를 골라 보세요`를 기기 TTS로 보냅니다. `game.js:21`에서 매 문항 자동 호출하며 다시 듣기도 같은 함수를 씁니다. `game.js:24,28`은 오답을 낸 경우에만 도움받음 처리하므로 이 음성을 듣고 고른 답은 독립 정답에 포함됩니다.

**영향 추론**: 예를 들어 三을 한국어 음성이 ‘삼’으로 읽으면 보기의 ‘석 삼’에서 독음이 사실상 제공됩니다. 음성 엔진별 실제 발음은 청취하지 않았으므로 항상 답이 노출된다고 단정하지 않습니다. 하지만 정답 한자를 읽기 엔진에 전달하는 코드 경로는 확인됩니다.

**수정 권고**: 한자→훈음 문제의 안내 음성은 “화면에 보이는 한자의 뜻과 소리를 골라 보세요”처럼 목표 한자를 제외하십시오. 훈음 읽기는 소개·정답 후 피드백에서 유지합니다.

**검증 제안**: name 문제의 TTS 입력 문자열에 정답 한자·훈·음이 없고, sound 문제에는 목표 훈음이 정상 포함되는지 확인하십시오. 이후 실제 한국어 음성도 청취해야 합니다. 기존 엔진 테스트로는 잡히지 않습니다.

#### 구현 P1-B. 소개·릴·포획 팝업에서 중간 종료가 차단됩니다

**소스 사실**: `game.js:12~13`은 `show(...,false)`인 팝업에 닫기 버튼을 만들지 않고 Escape 취소도 막습니다. 소개(15줄), 릴(25줄), 포획(28줄), 완료(29줄)가 모두 이 방식입니다. 회차 중단·쉬기·재개 함수는 없고, `start()`는 새 세션을 만듭니다. 소개와 진행 상태는 메모리에만 있습니다.

**영향**: 아이가 긴 소개나 연속 포획 중 쉬려면 브라우저 차원의 이동·새로고침이 필요합니다. 그때 이미 잡은 물고기는 저장되지만 미완료 회차·소개 지점은 복원하지 않습니다. 10번 소개 카드, 15번 릴과 포획 화면을 거치는 흐름에서 정상적인 중단 경로가 없는 것은 ‘약 5분’ 여부와 무관하게 수정할 부분입니다.

**수정 권고**: 모든 필수 팝업에 ‘오늘은 여기까지’를 제공하고, 이미 얻은 포획 기록을 유지하며 회차를 안전하게 종료하십시오. MVP에서는 이어하기를 구현하지 않아도 되지만 ‘다음에는 첫 소개부터 시작해요’를 명확히 안내하십시오. 단순히 Escape로 팝업을 닫기만 하면 `locked` 상태 등에서 멈출 수 있으므로 명시적인 세션 종료 처리가 필요합니다.

#### 구현 P1-C. 새 문제로 넘어갈 때 유효한 키보드 초점을 보장하지 않습니다

**소스 사실**: `game.js:11~12`는 팝업 이전 `lastFocus`가 연결되어 있으면 복원을 시도합니다. 하지만 시작 버튼은 숨겨지고(16줄), 선택 버튼은 정답 때 비활성화되며(24줄), 다음 문제에서는 전체 선택지 DOM이 교체됩니다(14줄). `nextQuestion()`은 새 문제나 새 선택지로 초점을 옮기지 않습니다. 최초 소개 뒤에는 숨긴 시작 버튼으로 복원하려는 경로도 있습니다.

**영향 추론**: 팝업을 닫을 때 숨김·비활성·곧 제거될 노드로 복원을 시도하므로 다음 선택지에 초점이 안정적으로 이어진다고 볼 수 없습니다. 브라우저별 실제 초점 위치는 실행하지 않았습니다. 새 질문은 live 영역도 아니어서 무음·키보드·화면낭독기 사용자는 문맥을 놓칠 수 있습니다.

**수정 권고**: 다음 문제 DOM을 만든 뒤 문제 제목에 `tabindex=-1`로 초점을 주거나 첫 활성 보기로 이동하십시오. 읽을 질문과 선택 순서를 일관되게 하십시오. `lastFocus` 복원은 지도·도감처럼 기존 화면으로 돌아가는 팝업에만 적용하고, 새 문제 전환은 별도로 처리하는 편이 명확합니다. 모달에도 제목을 `aria-labelledby`로 연결하십시오.

**검증 제안**: Tab·Enter만으로 소개→선택→릴 건너뛰기→포획→다음 문제를 여러 번 반복하고, 매 단계에 보이는 유효 초점과 질문 문맥이 남는지 브라우저에서 확인해야 합니다.

#### 구현 P2-D. 저장 실패 후에도 ‘저장됩니다’라고 완료 안내합니다

**소스 사실**: `game.js:6`의 `persist()`는 실패하면 경고를 띄우지만 성공 여부를 반환하지 않습니다. `game.js:29`는 무조건 “수집한 한자는 이 기기에 저장됩니다.”라고 알립니다. 저장 실패 경고 자체는 `index.html:18`에 마련되어 있습니다.

**영향**: 저장 차단·용량 오류 상황에서 서로 모순된 안내를 보여 줍니다. 모든 환경에서 저장이 실패한다는 뜻은 아닙니다.

**수정 권고**: 저장 성공 여부를 상태로 유지하고 완료 안내도 ‘이번 화면에만 남아 있어요’와 구분하십시오. 실패 시 경고가 보호자에게 보이도록 하고, 저장 여부를 진행 성공과 분리하십시오.

#### 구현 P2-E. 오답 뒤 재확인할 글자와 양방향 기록을 남기지 않습니다

**소스 사실**: `engine.js:7~9`의 저장 데이터는 글자별 `caught`, `independent`의 누적 수뿐입니다. `game.js:24`의 도움 여부는 포획 시 집계한 뒤 문항과 함께 사라지며, 다른 문제 뒤 다시 내기·다음 접속 우선 출제는 없습니다. 첫 10문항은 글자당 한 방향이고 월척은 무작위 5자이므로 모든 글자를 양방향으로 확인하지 않습니다.

**판단**: 도감에서 숙달이 아니라고 표시하므로 현재의 단순 ‘만남 기록’에는 허용할 수 있는 제한입니다. 다만 장기 설계의 복습이나 부모의 약한 글자 판단에 그대로 쓰기에는 정보가 부족합니다. 오늘 오답을 냈다가 다음 날 무엇을 다시 볼지 알 수 없습니다.

**수정 권고**: 완전한 간격 반복 전에라도 글자·문제 방향·마지막 도움 여부를 남기고, 도움받은 글자를 다음 회차의 소개 후 복습에 우선 넣으십시오. 같은 글자를 색·위치와 분리해 독립적으로 맞힐 기회가 필요합니다. 현재 카운트를 숙련도나 능력 등급으로 바꾸지 마십시오.

#### 구현 P2-F. 작은 화면에서는 핵심 오답 설명 한 곳이 숨겨집니다

**소스 사실**: `game.js:24`는 오답 피드백을 페이지 하단 `#status`와 `.guide`의 `#tip`에 씁니다. `style.css:1`의 650px 이하 규칙은 `.guide{display:none}`으로 숨깁니다. `index.html:18`의 상태 메시지는 도감·여정 footer 뒤에 있습니다. 문제 근처에는 오답 후 정답 비교·함께 보기 버튼이 없습니다.

**영향 추론**: 작은 세로 화면에서 하단 상태가 화면 밖이면 무음 사용자가 틀린 이유를 놓칠 수 있습니다. 실제 잘림·스크롤 위치는 브라우저로 확인하지 않았습니다.
